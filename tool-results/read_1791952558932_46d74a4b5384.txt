     7→# Project Engineering Skills & Standards
     8→
     9→## Purpose
    10→
    11→Use this file as the default engineering standard for all new web, SaaS, API, AI-agent, automation, dashboard, and e-commerce projects. The goal is to build software that is **fast, secure, maintainable, scalable, accessible, SEO-friendly, observable, and production-ready** from the beginning.
    12→
    13→---
    14→
    15→# 1. Core Engineering Principles
    16→
    17→- Prefer simple, boring, maintainable architecture over unnecessary complexity.
    18→- Design for production from the first implementation, not as a later cleanup task.
    19→- Reuse existing libraries and project utilities before creating custom replacements.
    20→- Keep business logic independent from UI, framework, database, and external providers where practical.
    21→- Use clear naming, small modules, typed interfaces, validation, and predictable error handling.
    22→- Never hard-code secrets, credentials, API keys, tokens, or environment-specific configuration.
    23→- Make important operations idempotent where possible.
    24→- Design APIs and database schemas around real use cases and expected growth.
    25→- Measure performance instead of guessing.
    26→- Automate repetitive checks with linting, formatting, tests, CI, and security scanning.
    27→
    28→---
    29→
    30→# 2. Project Discovery Before Coding
    31→
    32→Before implementation:
    33→
    34→1. Inspect the existing repository structure.
    35→2. Identify the framework, runtime, package manager, database, deployment target, and existing conventions.
    36→3. Read existing documentation and configuration files.
    37→4. Identify reusable components and utilities.
    38→5. Inspect database schema and migrations before changing data models.
    39→6. Identify authentication, authorization, integrations, queues, cron jobs, storage, and external APIs.
    40→7. Define functional requirements and non-functional requirements.
    41→8. Define expected traffic, data volume, concurrency, latency targets, and availability requirements.
    42→9. Identify deployment limitations such as shared hosting, cPanel, serverless, containers, or VPS.
    43→10. Produce an implementation plan before making large architectural changes.
    44→
    45→Do not rewrite working systems merely for stylistic reasons.
    46→

    49→# 3. System Design
    50→
    51→Every significant project should have a lightweight system design covering:
    52→
    53→- Users and roles
    54→- Main business workflows
    55→- Frontend architecture
    56→- Backend/API architecture
    57→- Database architecture
    58→- Authentication and authorization
    59→- File/object storage
    60→- Caching
    61→- Background jobs and queues
    62→- External integrations
    63→- Observability
    64→- Security boundaries
    65→- Deployment architecture
    66→- Backup and disaster recovery
    67→- Scaling strategy
    68→- Failure modes
    69→
    70→## Recommended logical architecture
    71→
    72→```text
    73→Browser / Mobile / Client
    74→        |
    75→        v
    76→CDN / Edge / WAF
    77→        |
    78→        v
    79→Frontend / BFF / API Gateway
    80→        |
    81→   +----+----------------+
    82→   |                     |
    83→   v                     v
    84→Application API      Background Jobs
    85→   |                     |
    86→   +----------+----------+
    87→              |
    88→       Service / Domain Layer
    89→              |
    90→     +--------+---------+
    91→     |        |         |
    92→     v        v         v
    93→ Database   Cache    Object Storage
    94→     |
    95→     v
    96→Backups / Replicas
    97→```
    98→
    99→For small projects, keep this logical separation without creating unnecessary microservices.
   100→
   101→## Monolith vs services
   102→
   103→Prefer a modular monolith until independent deployment, scaling, ownership, or reliability requirements justify service separation.
   104→
   105→Use microservices only when there is a clear operational reason such as:
   106→
   107→- independently scaling workloads
   108→- independently deploying high-risk components
   109→- strict isolation requirements
   110→- separate team ownership
   111→- different runtime requirements
   112→- asynchronous/event-driven workloads at meaningful scale

   116→# 4. Fast Website / Performance Engineering
   117→
   118→Performance is a first-class feature.
   119→
   120→## Target principles
   121→
   122→Aim for:
   123→
   124→- Fast first response
   125→- Minimal JavaScript
   126→- Minimal CSS
   127→- Small HTML payloads
   128→- Optimized images
   129→- Efficient database queries
   130→- Aggressive but safe caching
   131→- CDN/edge delivery where useful
   132→- Streaming or progressive rendering for expensive content
   133→- No unnecessary client-side work
   134→
   135→## Loading strategy
   136→
   137→### Critical rendering path
   138→
   139→1. Return useful HTML quickly.
   140→2. Inline only genuinely critical CSS when justified.
   141→3. Defer non-critical JavaScript.
   142→4. Preload only high-priority resources.
   143→5. Avoid render-blocking third-party scripts.
   144→6. Lazy-load below-the-fold media.
   145→7. Reserve image dimensions to prevent layout shift.
   146→8. Use modern image formats such as AVIF/WebP where supported.
   147→9. Compress text assets with Brotli or gzip.
   148→10. Use long-lived immutable caching for fingerprinted static assets.
   149→
   150→### JavaScript
   151→
   152→- Prefer server rendering or static rendering for content-heavy pages.
   153→- Ship only the JavaScript required for the current page.
   154→- Split large bundles.
   155→- Lazy-load expensive components.
   156→- Remove unused dependencies.
   157→- Avoid large client-side state stores unless needed.
   158→- Avoid hydration of components that do not need interactivity.
   159→- Use Web Workers for appropriate CPU-heavy browser tasks.
   160→
   161→### Images
   162→
   163→- Resize images to their actual display size.
   164→- Generate responsive variants with `srcset`/`sizes`.
   165→- Use `loading="lazy"` for non-critical images.
   166→- Do not lazy-load the primary above-the-fold hero image when it is the LCP element.
   167→- Use `fetchpriority="high"` selectively for the primary LCP resource.
   168→- Strip unnecessary metadata.
   169→- Generate thumbnails rather than downloading full-size images everywhere.
   170→
   171→### Fonts
   172→
   173→- Use a limited number of font families and weights.
   174→- Prefer self-hosted fonts when appropriate.
   175→- Preload only critical fonts.
   176→- Use `font-display: swap` or an appropriate fallback strategy.
   177→- Avoid loading dozens of unused font weights.

   181→# 5. Core Web Vitals
   182→
   183→Track and optimize:
   184→
   185→- **LCP** — Largest Contentful Paint
   186→- **INP** — Interaction to Next Paint
   187→- **CLS** — Cumulative Layout Shift
   188→
   189→Also monitor:
   190→
   191→- TTFB
   192→- FCP
   193→- total transfer size
   194→- JavaScript execution time
   195→- long tasks
   196→- API latency
   197→- database latency
   198→
   199→Performance work should be validated with real measurements in addition to local development testing.
   200→
   201→---
   202→
   203→# 6. Backend Performance
   204→
   205→- Avoid N+1 database queries.
   206→- Select only required columns.
   207→- Add indexes based on actual query patterns.
   208→- Paginate large collections.
   209→- Use cursor pagination for very large datasets where appropriate.
   210→- Cache expensive and stable reads.
   211→- Batch writes when appropriate.
   212→- Use connection pooling.
   213→- Move long-running operations to background jobs.
   214→- Stream large files instead of loading them fully into memory.
   215→- Apply request timeouts to external services.
   216→- Use retries with exponential backoff only for retryable failures.
   217→- Prevent retry storms.
   218→- Use circuit breakers where external dependency failures can cascade.
   219→
   220→---
   221→
   222→# 7. Database Design
   223→
   224→- Use migrations for schema changes.
   225→- Use foreign keys and constraints where appropriate.
   226→- Add indexes for real query patterns.
   227→- Avoid indexing every column.
   228→- Use transactions for multi-step consistency requirements.
   229→- Keep large blobs out of relational tables when object storage is more appropriate.
   230→- Add audit fields such as `created_at` and `updated_at` where useful.
   231→- Use soft deletion only when there is a concrete business requirement.
   232→- Plan retention and archival for high-volume tables.
   233→- Back up production databases automatically.
   234→- Test restoration, not only backup creation.
   235→
   236→---
   237→
   238→# 8. Caching Strategy
   239→
   240→Use cache layers deliberately:
   241→
   242→```text
   243→Browser Cache
   244→     -> CDN / Edge Cache
   245→     -> Application Cache
   246→     -> Database
   247→```
   248→
   249→Possible technologies include browser HTTP caching, CDN caching, Redis, in-process caches, and database query/result caching.
   250→
   251→Rules:
   252→
   253→- Define cache keys clearly.
   254→- Define TTLs.
   255→- Define invalidation rules.
   256→- Avoid caching private user data in shared caches.
   257→- Prevent cache stampedes.
   258→- Never rely on cache as the only source of durable data.
   259→
   260→---
   261→
   262→# 9. API Design
   263→
   264→- Version public APIs when compatibility requires it.
   265→- Use consistent resource naming.
   266→- Validate all input at the boundary.
   267→- Return predictable error structures.
   268→- Use appropriate HTTP status codes.
   269→- Support pagination, filtering, sorting, and search intentionally.
   270→- Apply authentication and authorization to every protected operation.
   271→- Add rate limits to abuse-prone endpoints.
   272→- Use idempotency keys for operations where duplicate requests can cause damage.
   273→- Document APIs with OpenAPI where appropriate.
   274→- Never expose internal stack traces or secrets to clients.

   278→# 10. Security
   279→
   280→Security must be designed into the system rather than added after deployment.
   281→
   282→## Application security
   283→
   284→- Validate and sanitize untrusted input.
   285→- Use parameterized queries/ORM protections against SQL injection.
   286→- Protect against XSS.
   287→- Protect state-changing requests against CSRF where applicable.
   288→- Prevent SSRF in URL-fetching features.
   289→- Validate file uploads by type, size, extension, content, and storage location.
   290→- Prevent path traversal.
   291→- Use secure session handling.
   292→- Apply least privilege.
   293→- Enforce authorization server-side; never trust UI restrictions.
   294→- Avoid exposing sensitive information in logs.
   295→- Add security headers where appropriate.
   296→- Configure CORS narrowly.
   297→- Use HTTPS in production.
   298→- Keep dependencies patched.
   299→
   300→## Authentication
   301→
   302→- Store passwords using strong password hashing such as Argon2id or an appropriate modern equivalent.
   303→- Never store plaintext passwords.
   304→- Support secure session expiration and revocation.
   305→- Protect login and password-reset endpoints against abuse.
   306→- Use MFA for sensitive applications where appropriate.
   307→- Rotate compromised credentials immediately.
   308→
   309→## Secrets
   310→
   311→Never commit:
   312→
   313→- API keys
   314→- database passwords
   315→- private keys
   316→- OAuth client secrets
   317→- JWT signing secrets
   318→- cloud credentials
   319→
   320→Use environment variables or a proper secret manager.
   321→
   322→## Security headers
   323→
   324→Consider:
   325→
   326→- Content-Security-Policy
   327→- Strict-Transport-Security
   328→- X-Content-Type-Options
   329→- Referrer-Policy
   330→- Permissions-Policy
   331→- frame-ancestors / appropriate clickjacking protection
   332→
   333→Do not blindly copy a header configuration; test it against application requirements.
   334→

   337→# 11. SEO
   338→
   339→For public websites, implement technical SEO from the beginning.
   340→
   341→- Semantic HTML.
   342→- Correct title and meta description.
   343→- Canonical URLs.
   344→- XML sitemap.
   345→- robots.txt.
   346→- Open Graph metadata.
   347→- Twitter/X card metadata where useful.
   348→- Structured data/schema where applicable.
   349→- Clean URL architecture.
   350→- Proper heading hierarchy.
   351→- Internal linking.
   352→- 404 and redirect handling.
   353→- Pagination/canonical strategy for large collections.
   354→- Fast mobile rendering.
   355→- Accessible navigation.
   356→- Avoid indexing duplicate, private, filtered, or low-value URLs unintentionally.
   357→
   358→For dynamic sites, generate metadata from authoritative content rather than duplicating it manually.
   359→

   361→
   362→# 12. Accessibility
   363→
   364→Target WCAG-aligned accessible interfaces.
   365→
   366→- Use semantic HTML first.
   367→- Keyboard navigation must work.
   368→- Provide visible focus states.
   369→- Use labels for form controls.
   370→- Provide useful alt text for meaningful images.
   371→- Mark decorative images appropriately.
   372→- Maintain adequate color contrast.
   373→- Do not rely on color alone to communicate state.
   374→- Use ARIA only when native HTML is insufficient.
   375→- Support screen readers for important workflows.
   376→- Respect reduced-motion preferences.
   377→
   378→---
   379→
   380→# 13. Frontend Architecture
   381→
   382→- Use reusable components.
   383→- Keep components focused.
   384→- Separate presentation from business logic where practical.
   385→- Keep forms validated on both client and server.
   386→- Handle loading, empty, success, error, and permission states.
   387→- Use optimistic UI only where rollback is well-defined.
   388→- Avoid unnecessary global state.
   389→- Preserve URL state for useful filters/search where appropriate.
   390→- Design responsive layouts from mobile to desktop.
   391→- Avoid layout shifts caused by asynchronous content.
   392→
   393→For Next.js or similar frameworks:
   394→
   395→- Prefer server components/rendering for non-interactive content.
   396→- Keep client components small.
   397→- Use route-level code splitting.
   398→- Cache stable server data appropriately.
   399→- Avoid accidentally converting large parts of the application into client components.
   400→
   401→---
   402→
   403→# 14. UX Standards
   404→
   405→Every important page should handle:
   406→
   407→- loading state
   408→- empty state
   409→- error state
   410→- success feedback
   411→- permission denied state
   412→- offline/network failure where applicable
   413→- destructive action confirmation
   414→
   415→Interfaces should be responsive, keyboard-friendly, and consistent.
   416→
   417→Avoid unnecessary animations, popups, spinners, and blocking dialogs.
   418→
   419→---
   420→
   421→# 15. AI / Agent Projects
   422→
   423→For AI systems:
   424→
   425→- Separate model provider configuration from business logic.
   426→- Support provider fallback where reliability requires it.
   427→- Use structured outputs when possible.
   428→- Validate model outputs before executing actions.
   429→- Require approval for high-impact or destructive actions.
   430→- Apply tool-level permissions.
   431→- Log model/tool traces without leaking secrets.
   432→- Bound context size and token usage.
   433→- Cache deterministic or reusable work where appropriate.
   434→- Add timeouts and retries for model APIs.
   435→- Design provider abstraction so models can be replaced.
   436→- Never allow model-generated instructions to bypass authorization.
   437→- Treat retrieved web/file content as untrusted input.
   438→- Add prompt-injection defenses for tool-using agents.
   439→
   440→Recommended agent flow:
   441→
   442→```text
   443→User Request
   444→    -> Intent / Task Analysis
   445→    -> Permission Check
   446→    -> Plan
   447→    -> Tool Selection
   448→    -> Tool Execution
   449→    -> Validation
   450→    -> Optional Human Approval
   451→    -> Result
   452→    -> Audit / Trace
   453→```

   457→# 16. Scraping / Crawling Systems
   458→
   459→For crawlers and website audit tools:
   460→
   461→- Respect robots.txt and applicable site policies.
   462→- Implement concurrency limits.
   463→- Use request timeouts.
   464→- Retry only transient failures.
   465→- Rotate proxies only when legitimately required and permitted.
   466→- Deduplicate URLs and content.
   467→- Normalize URLs.
   468→- Detect canonical URLs.
   469→- Store crawl state incrementally.
   470→- Stream or batch large exports.
   471→- Avoid loading browser automation for pages that can be fetched with HTTP.
   472→- Use browser rendering only when required by JavaScript behavior.
   473→- Cache reusable resources.
   474→- Track status codes, redirects, latency, content type, and crawl errors.
   475→- Prevent infinite crawl loops and unbounded URL generation.
   476→

   479→# 17. File Uploads and Storage
   480→
   481→- Store uploads outside executable web roots where possible.
   482→- Generate server-side filenames.
   483→- Limit file size.
   484→- Validate MIME type and actual file content.
   485→- Scan files where risk warrants it.
   486→- Prevent executable uploads.
   487→- Use object storage for large media when appropriate.
   488→- Use signed URLs for private downloads.
   489→- Apply retention and cleanup policies.
   490→

   493→# 18. Background Jobs
   494→
   495→Use queues for:
   496→
   497→- email sending
   498→- image processing
   499→- video processing
   500→- scraping
   501→- report generation
   502→- AI workloads
   503→- imports/exports
   504→- scheduled maintenance
   505→
   506→Each job should have:
   507→
   508→- unique/job ID
   509→- retry policy
   510→- timeout
   511→- status
   512→- error details
   513→- idempotency strategy
   514→- dead-letter handling where appropriate
   515→- progress reporting for long operations
   516→
   517→---
   518→
   519→# 19. Observability
   520→
   521→Production systems should provide:
   522→
   523→- structured logs
   524→- request IDs / correlation IDs
   525→- metrics
   526→- error tracking
   527→- health checks
   528→- dependency health checks
   529→- performance measurements
   530→- audit logs for sensitive actions
   531→
   532→Track at minimum:
   533→
   534→- request rate
   535→- error rate
   536→- latency
   537→- database latency
   538→- queue depth
   539→- job failures
   540→- cache hit/miss rate where relevant
   541→- resource utilization
   542→
   543→Never log passwords, tokens, private keys, full payment details, or unnecessary personal data.
   544→

   546→
   547→# 20. Reliability and Failure Design
   548→
   549→Design for failure:
   550→
   551→- external APIs can fail
   552→- databases can become unavailable
   553→- queues can back up
   554→- DNS/CDN can fail
   555→- users can submit duplicate requests
   556→- workers can crash midway through a job
   557→- deployments can fail
   558→
   559→Use:
   560→
   561→- timeouts
   562→- retries with backoff
   563→- idempotency
   564→- graceful degradation
   565→- circuit breakers where appropriate
   566→- health checks
   567→- transactional boundaries
   568→- rollback/feature flags for risky releases
   569→- backups and tested restoration procedures
   570→

   572→
   573→# 21. Deployment
   574→
   575→Before production:
   576→
   577→- production environment variables configured
   578→- HTTPS enabled
   579→- database migrations tested
   580→- backups configured
   581→- restore process tested
   582→- error monitoring enabled
   583→- logging configured
   584→- security headers reviewed
   585→- CORS reviewed
   586→- rate limiting reviewed
   587→- cron/queue workers verified
   588→- storage permissions reviewed
   589→- build artifacts verified
   590→- cache behavior tested
   591→- rollback procedure documented
   592→
   593→For restricted shared hosting/cPanel environments, prefer architecture that matches available runtimes. If Node.js is unavailable, do not assume a Next.js server can run there; consider static export, PHP backend, a supported runtime, or external application hosting.

   597→# 22. Testing
   598→
   599→Use multiple testing layers:
   600→
   601→### Unit tests
   602→
   603→Business rules, utility functions, validators, transformations.
   604→
   605→### Integration tests
   606→
   607→Database, APIs, queues, storage, and external-service adapters.
   608→
   609→### End-to-end tests
   610→
   611→Critical user journeys such as authentication, checkout, dashboard workflows, and administration.
   612→
   613→### Performance tests
   614→
   615→Measure representative workloads and concurrency.
   616→
   617→### Security tests
   618→
   619→Check authentication, authorization, injection risks, uploads, SSRF, dependency vulnerabilities, and exposed secrets.
   620→
   621→Do not treat high test coverage as proof of correctness; test important behavior and failure modes.
   622→

   625→# 23. CI/CD Quality Gates
   626→
   627→A production repository should ideally run:
   628→
   629→```text
   630→Install
   631→  -> Type Check
   632→  -> Lint
   633→  -> Format Check
   634→  -> Unit Tests
   635→  -> Integration Tests
   636→  -> Build
   637→  -> Security / Dependency Scan
   638→  -> Deployment
   639→  -> Smoke Test
   640→```
   641→
   642→Block deployment when critical checks fail.

   646→# 24. Code Quality
   647→
   648→Use:
   649→
   650→- TypeScript strict mode where applicable.
   651→- Python type hints where practical.
   652→- ESLint/formatter or equivalent tooling.
   653→- Ruff/Black/MyPy or project-appropriate Python tooling.
   654→- Clear module boundaries.
   655→- Small functions.
   656→- Explicit error handling.
   657→- No dead code.
   658→- No duplicated business logic.
   659→- No unexplained magic constants.
   660→
   661→Comments should explain **why**, not merely repeat what the code does.

   665→# 25. Dependency Management
   666→
   667→Before adding a dependency:
   668→
   669→1. Check whether the framework already provides the feature.
   670→2. Check maintenance activity.
   671→3. Check license compatibility.
   672→4. Check bundle/runtime impact.
   673→5. Check security history.
   674→6. Check whether a smaller dependency solves the problem.
   675→
   676→Keep dependencies updated, but test upgrades before production deployment.

   724→# 28. Project Structure
   725→
   726→Use a structure appropriate to the framework, but keep responsibilities clear.
   727→
   728→Example:
   729→
   730→```text
   731→project/
   732→├── app/ or src/
   733→│   ├── components/
   734→│   ├── pages/ or routes/
   735→│   ├── features/
   736→│   ├── services/
   737→│   ├── domain/
   738→│   ├── repositories/
   739→│   ├── validators/
   740→│   ├── lib/
   741→│   └── config/
   742→├── tests/
   743→├── scripts/
   744→├── migrations/
   745→├── public/
   746→├── docs/
   747→├── .env.example
   748→├── README.md
   749→├── ARCHITECTURE.md
   750→└── SECURITY.md
   751→```
   752→
   753→Do not force this exact structure onto every framework; use the same separation of concerns with framework-native conventions.

   793→# 30. Default Definition of Done
   794→
   795→A feature is not complete when the code merely works locally.
   796→
   797→A feature is complete when:
   798→
   799→1. The intended behavior works.
   800→2. Invalid input is handled safely.
   801→3. Permissions are enforced server-side.
   802→4. Loading, empty, success, and failure states are handled.
   803→5. Data integrity is preserved.
   804→6. Performance is acceptable for the expected workload.
   805→7. Security implications have been reviewed.
   806→8. Tests cover important behavior.
   807→9. Logs/metrics exist where operationally useful.
   808→10. Documentation is updated.
   809→11. Deployment behavior is verified.
   810→12. The implementation does not introduce unnecessary technical debt.

   814→# 31. Fast-by-Default Rules
   815→
   816→For every new website, ask:
   817→
   818→- Can this page be rendered on the server?
   819→- Can this JavaScript be removed?
   820→- Can this API call happen server-side?
   821→- Can this request be cached?
   822→- Can this image be smaller?
   823→- Can this dependency be removed?
   824→- Can this database query be reduced?
   825→- Can this work happen asynchronously?
   826→- Can this third-party script be removed or deferred?
   827→- Can this page load useful content before non-critical content?
   828→
   829→**Performance is not a final optimization phase. It is an architectural requirement.**

   833→# 32. Default AI Coding-Agent Instructions
   834→
   835→When an AI coding agent works on a project using this file:
   836→
   837→1. Inspect before editing.
   838→2. Understand existing architecture before introducing new patterns.
   839→3. Make the smallest safe change that solves the problem.
   840→4. Preserve working functionality.
   841→5. Do not silently remove features.
   842→6. Validate changes with tests, lint, type checks, and build checks where available.
   843→7. Review security implications of every new endpoint, upload, integration, credential, and external request.
   844→8. Review performance implications of every new dependency, client component, query, API call, image, and third-party script.
   845→9. Report files changed and validation performed.
   846→10. If a requirement conflicts with deployment limitations, explain the constraint and implement the closest production-safe architecture rather than pretending the unsupported runtime exists.
